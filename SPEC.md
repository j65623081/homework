## Что делаем

HTTP-API для заметок с тегами: создание, чтение, изменение, удаление и список с фильтром
по тегу и подстроке. Хранилище — один JSON-файл на диске, без базы данных.

## Для кого и зачем

Пользователь — разработчик клиента (мобильного или веб), которому нужен предсказуемый
бэкенд для личных заметок. Его проблема не в объёме функций, а в том, что поведение API
на границах обычно не описано: непонятно, что вернётся на фильтр без совпадений, что
станет с тегом `« Работа »` и что будет, если повторить неудавшийся запрос.

Поэтому ценность здесь — не набор эндпоинтов, а **контракт**: у каждого запроса есть
заранее описанный ожидаемый ответ, с которым сверяется факт.

## Модель данных

Заметка:

| Поле | Тип | Обязательное | Правила |
|---|---|---|---|
| `id` | string (UUID v4) | выдаёт сервер | Клиент не может задать или изменить |
| `title` | string | да | После `trim` — от 1 до 200 символов |
| `body` | string | нет | До 10 000 символов, по умолчанию `""` |
| `tags` | string[] | нет | До 10 штук, по умолчанию `[]`, правила нормализации ниже |
| `created_at` | string | выдаёт сервер | ISO 8601, UTC, не меняется |
| `updated_at` | string | выдаёт сервер | ISO 8601, UTC |

### Нормализация тегов

Выполняется молча, при создании и при обновлении, в этом порядке:

1. `trim` — убираются пробелы по краям
2. Приведение к нижнему регистру
3. Дедупликация с сохранением порядка первого вхождения

**Исключение:** тег, ставший пустым после `trim`, — это ошибка клиента, а не мусор,
который надо подчистить. Такой запрос отклоняется с 422 и указанием индекса.

Ответ на `POST` и `PUT` всегда содержит **уже нормализованные** теги — клиент видит,
что с ними сделали, и может сверить.

Длина одного тега после нормализации — от 1 до 30 символов.

**Потолок в 10 тегов считается до дедупликации, а не после.**

> Записано на шаге 6 (2026-08-17). Решение принималось при реализации, но в спеке
> зафиксировано не было, а формулировка «до 10 штук» допускала оба прочтения.

Одиннадцать одинаковых тегов дают `422`, хотя после нормализации остался бы один.
Ограничение относится к размеру присланного тела, а не к размеру результата: иначе
клиент мог бы прислать тысячу дублей, и сервис обязан был бы их все обработать,
прежде чем выяснить, что тег там один.

Альтернатива — считать потолок **после** дедупликации — рассмотрена и отклонена.
При таком варианте стоимость обработки запроса перестаёт зависеть от заявленного
лимита: сервису пришлось бы сначала нормализовать и дедуплицировать произвольно
большой список, и только потом решать, помещается ли результат в 10 штук. Проверка
до дедупликации отклоняет такой запрос, не читая его целиком по смыслу.

## Контракт API

Базовый путь — `/api`. Тело запроса и ответа — `application/json; charset=utf-8`.

### 1. `GET /api/notes` — список с фильтром

Параметры строки запроса:

| Параметр | Тип | По умолчанию | Правила |
|---|---|---|---|
| `tag` | string | — | Сравнение по нормализованному значению |
| `q` | string | — | Подстрока в `title` или `body`, регистронезависимо |
| `limit` | int | 20 | От 1 до 100 |
| `offset` | int | 0 | От 0, без верхней границы |

Сортировка — `created_at` по убыванию; при равенстве — по `id` по возрастанию,
чтобы порядок был детерминированным и тесты не «моргали».

`200 OK`:

```json
{
  "data": [ { "id": "...", "title": "...", "body": "...", "tags": ["работа"],
              "created_at": "2026-08-16T10:00:00Z", "updated_at": "2026-08-16T10:00:00Z" } ],
  "meta": { "total": 42, "limit": 20, "offset": 0 }
}
```

`total` — число записей, подходящих под фильтр, **до** применения `limit` и `offset`.

Поведение на границах:

| Случай | Ответ |
|---|---|
| `?tag=несуществующий` | `200`, `data: []`, `total: 0` |
| `?offset=` больше числа записей, в том числе многократно | `200`, `data: []`, `total` — реальное число |
| `?limit=0`, `?limit=-1`, `?limit=101`, `?limit=abc` | `422`, `fields: {"limit": [...]}` |
| `?offset=-1`, `?offset=abc` | `422`, `fields: {"offset": [...]}` |

> Формат `fields: {"limit": [...]}` — сокращение для этой таблицы. Полная форма ошибки
> описана в разделе «Формат ошибки» ниже; она одна для всего контракта, отдельного
> формата для `GET /api/notes` нет.

**У `offset` сознательно нет верхней границы.** Найдено на аудите шага 7 (2026-08-17):
`?offset=999999999999999999999` не даёт `422`, а тихо приводится к максимуму типа
`int`. Не расхождение с контрактом — контракт границу не заявлял, — но недосказанность,
которую стоит закрыть явно, а не оставлять на догадку. У `limit` верхняя граница есть
не просто из общего принципа «валидировать строго», а по конкретной причине: без неё
один запрос мог бы выгрузить весь файл. У `offset` такой причины нет — значение больше
числа записей уже обработано выше как валидный случай с пустым результатом, поэтому
верхний предел ничего не защищает и вводить его не будем.

### 2. `POST /api/notes` — создание

Тело: `title` (обяз.), `body`, `tags`.

- `201 Created`, заголовок `Location: /api/notes/{id}`, тело — `{ "data": { ...заметка } }`
- `422` — валидация не прошла
- `400` — тело не является корректным JSON

### 3. `GET /api/notes/{id}`

- `200 OK` — `{ "data": { ...заметка } }`
- `404` — `code: not_found`

### 4. `PUT /api/notes/{id}` — обновление

Полная замена изменяемых полей. `id` и `created_at` неизменяемы.

- `200 OK` — `{ "data": { ...заметка } }`
- `404` — записи нет. **Upsert не выполняется**: создание идёт только через `POST`
- `422` — валидация не прошла
- `400` — тело не является корректным JSON

**Повторная отправка того же тела:** `200` с тем же телом ответа. Если нормализованное
тело совпадает с текущим состоянием записи, файл не перезаписывается и `updated_at`
не меняется — второй ответ побайтово равен первому.

### 5. `DELETE /api/notes/{id}`

- `204 No Content` — тела нет
- `404` — записи нет. Повторное удаление даёт `404`, а не `204`

### 6. `POST /api/notes/import` — импорт пачкой

> Добавлено на шаге 1 ДЗ №2 (2026-08-30), до реализации. Все решения ниже приняты
> человеком по вопросам агента либо приняты агентом с явно названной альтернативой.

Загрузка нескольких заметок одним запросом. Источник пачки — внешний файл, то есть
**недоверенные данные**: см. отдельный подраздел ниже.

#### Тело запроса — два формата

**A. `Content-Type: application/json`**

```json
{ "notes": [ { "title": "…", "body": "…", "tags": ["…"] } ] }
```

**B. `Content-Type: multipart/form-data`**, поле `file` — файл в UTF-8, содержащий
ровно тот же JSON-объект `{ "notes": [ … ] }`.

Любой другой `Content-Type` → `415` `unsupported_media_type`. Имя файла, его MIME-тип
и прочие метаданные **не влияют ни на что** — разбирается только содержимое.

Элемент массива подчиняется тем же правилам, что тело `POST /api/notes`: `title`
обязателен, `body` и `tags` необязательны, нормализация тегов та же, неизвестные поля
внутри элемента отклоняют **этот элемент**, а не всю пачку.

#### Заголовок `Idempotency-Key` — обязателен

Строка от 8 до 128 символов, допустимые символы `[A-Za-z0-9_-]`. Отсутствует или
не подходит под формат → `422` `idempotency_key_invalid`.

> **Альтернатива — сделать ключ необязательным, как в Stripe, — рассмотрена и отклонена.**
> Без ключа повторная отправка пачки из двухсот заметок по таймауту молча удваивает
> хранилище, и это самая дорогая ошибка в этой фиче: она не диагностируется по коду
> ответа, потому что оба ответа успешные. Цена решения названа честно — клиент обязан
> сгенерировать ключ даже для одноразового импорта.

#### Потолки

| Что | Предел | При превышении |
|---|---|---|
| Заметок в пачке | 200 | `413` `import_too_large` |
| Размер тела или файла | 2 МБ | `413` `import_too_large` |
| Записей в реестре ключей | 500 | вытесняется самая старая по `created_at` |

Оба потолка проверяются **до** разбора содержимого — по той же логике, что и потолок
тегов до дедупликации: стоимость обработки запроса не должна зависеть от того, что
клиент прислал.

Пустая пачка `{"notes": []}` → `422` `validation_failed`. Импорт нуля заметок — почти
наверняка ошибка на стороне клиента, и тихий успех её спрячет.

#### Ответ — частичный успех

`200 OK`. Пачка разобрана; какие-то элементы записаны, какие-то отклонены.

```json
{
  "imported": 97,
  "rejected": 3,
  "idempotent_replay": false,
  "notes": [ { "id": "…", "title": "…", "body": "…", "tags": [], "created_at": "…", "updated_at": "…" } ],
  "errors": [
    { "index": 12, "code": "validation_failed", "fields": { "title": ["Поле обязательно для заполнения"] } },
    { "index": 44, "code": "unknown_fields",    "fields": { "titel": ["Поля нет в контракте"] } }
  ]
}
```

- `notes` — успешно созданные, в порядке следования во входной пачке;
- `errors[].index` — индекс элемента **во входной пачке**, а не в `notes`;
- `errors[].code` — код из того же закрытого перечня, что и обычные ошибки.

**`200` отдаётся и тогда, когда `imported` равен нулю.**

> **Альтернатива — отвечать `422`, если не записалось ничего, — рассмотрена и отклонена.**
> Граница «ноль против одного» создала бы два разных формата ответа на один и тот же
> запрос, различающихся только данными: клиенту пришлось бы разбирать успех и ошибку
> по-разному в зависимости от того, повезло ли хоть одной заметке. Отчёт по индексам
> и есть результат запроса — клиенту нужен разбор, а не отказ.

Ошибки уровня всей пачки (`malformed_json`, `unsupported_media_type`, `import_too_large`,
`idempotency_key_invalid`, `idempotency_key_conflict`, `storage_corrupted`) отдаются
в **едином формате ошибки**, а не в `errors[]`: они относятся к запросу целиком,
и ни одна заметка при них не записывается.

#### Идемпотентность

При успешном разборе пачки сервис запоминает ключ вместе с хешем запроса и телом ответа.

| Повтор | Ответ |
|---|---|
| Тот же ключ, тот же хеш запроса | `200`, **ровно то же тело**, что в первый раз, но `idempotent_replay: true`. Хранилище не трогается |
| Тот же ключ, **другой** хеш запроса | `409` `idempotency_key_conflict`. Ничего не записывается |
| Другой ключ, то же содержимое | Обычный импорт. Заметки создаются повторно — это не дубликаты, а намеренный второй импорт |

`request_hash` — SHA-256 от разобранного и канонизированного содержимого пачки. Для
формата B хеш считается от содержимого файла, а не от границ multipart: один и тот же
файл, отправленный дважды, обязан дать один хеш.

Последняя строка таблицы — сознательная граница. **Идемпотентность здесь про доставку,
а не про дедупликацию.** Сервис не пытается угадать, что клиент «уже импортировал такое»;
он отвечает за то, что один запрос, отправленный дважды, выполнится один раз.

#### Реестр ключей — отдельный файл

`storage/app/import_keys.json`, объект «ключ → запись»:

```json
{ "batch-2026-08-30-001": { "request_hash": "…", "response": { }, "created_at": "…" } }
```

Формат `notes.json` **не меняется** — он остаётся массивом заметок, и все сценарии
и тесты, написанные для него в ДЗ №1, остаются в силе без правок.

**Порядок записи зафиксирован: сначала `notes.json`, потом `import_keys.json`.**
Оба файла пишутся атомарно (временный файл плюс переименование), но транзакции между
двумя файлами нет, и падение процесса между записями возможно.

> Из двух вариантов выбран тот, где сбой видим. При этом порядке падение между записями
> означает «заметки записаны, ключ не зафиксирован»: повтор создаст дубли, клиент их
> увидит в списке и сможет удалить. Обратный порядок означает «ключ есть, заметок нет»:
> повтор вернёт сохранённый успешный отчёт с `imported: 97`, а заметок в хранилище
> не будет. Дубли — видимая и исправимая авария, ложный успех — тихая потеря данных.

TTL у ключей нет: срок жизни требует часов и фонового процесса, которых в этой задаче
нет. Рост файла ограничен потолком в 500 записей с вытеснением самых старых.

#### Содержимое заметок — данные, а не инструкции

Часть контракта, потому что проверяется в приёмке.

- Сервис **не интерпретирует** текст в `title`, `body` и `tags`. Что бы там ни было
  написано — это значение поля.
- Сервис **не выполняет** ничего из импортированного файла и не меняет своё поведение
  в зависимости от его содержания.
- Ответ отдаёт текст **как есть**, без экранирования: экранирование — обязанность
  того, кто выводит. Для веб-интерфейса это записано отдельным критерием приёмки.
- Метаданные файла (имя, MIME-тип, произвольные поля multipart) игнорируются.

### Формат ошибки

Единый для всех ответов с кодом 4xx и 5xx. Трассировки стека наружу не выходят никогда.

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Тело запроса не прошло валидацию",
    "fields": {
      "title": ["Поле обязательно для заполнения"],
      "tags.2": ["Тег не может быть пустым"]
    }
  }
}
```

| Код | HTTP | Когда |
|---|---|---|
| `malformed_json` | 400 | Тело не разбирается как JSON |
| `validation_failed` | 422 | Значения полей не прошли проверку |
| `unknown_fields` | 422 | В теле есть поля, которых нет в контракте |
| `not_found` | 404 | Записи с таким `id` нет, либо такого маршрута или метода не существует |
| `storage_corrupted` | 500 | Файл-хранилище не разбирается как JSON |
| `internal_error` | 500 | Непредвиденная ошибка сервера |
| `unsupported_media_type` | 415 | `Content-Type` не `application/json` и не `multipart/form-data` (только импорт) |
| `import_too_large` | 413 | Больше 200 заметок в пачке или больше 2 МБ тела (только импорт) |
| `idempotency_key_invalid` | 422 | `Idempotency-Key` отсутствует или не подходит под формат (только импорт) |
| `idempotency_key_conflict` | 409 | Ключ уже использован с другим содержимым запроса (только импорт) |

Четыре последних кода добавлены на шаге 1 ДЗ №2 (2026-08-30) под эндпоинт импорта,
до написания кода. Каждый закрывает случай, который иначе пришлось бы прятать
в `validation_failed`, теряя причину отказа:

- `unsupported_media_type` понадобился потому, что у импорта **два** допустимых формата
  тела, и третий надо отклонять внятно, а не как «ошибку валидации полей»;
- `import_too_large` отделяет «прислано слишком много» от «прислано неправильно» —
  клиенту в первом случае надо разбить пачку, а не чинить данные;
- `idempotency_key_invalid` и `idempotency_key_conflict` относятся к **заголовку**,
  а не к телу. Уложить их в `validation_failed` означало бы отправить клиента искать
  ошибку в `fields`, где её нет.

При этих кодах поле `fields` отсутствует: ошибка не привязана к полю тела.

Две последние строки добавлены на шаге 5 по решению человека — перечень оказался
неполным. `internal_error` закрывает всё, что не предусмотрено: нет прав на запись,
диск полон, ошибка в самом коде. Клиент видит только код и общую фразу, без деталей.
Обращение к несуществующему маршруту и обращение с неподдерживаемым методом
(например, `PATCH /api/notes/{id}`) отдают `404` `not_found`: отдельный код для `405`
не вводится сознательно, чтобы не расширять контракт ради случая, которого нет
ни в одном сценарии.

**Неизвестные поля отклоняются, а не игнорируются.** `fields` содержит их перечень.
Решение принято сознательно: опечатка вида `titel` вместо `title` иначе обнаружится
не сразу, а как «поле почему-то не сохраняется».

## Сценарии

1. **Создание и чтение.** Клиент отправляет `POST` с заголовком и тегами `["Работа", " работа "]`
   → получает `201` и заметку с тегами `["работа"]`. Запрашивает её по `id` → `200`, те же данные.
2. **Список с фильтром.** `GET /api/notes?tag=работа&limit=5` → пять последних заметок
   с этим тегом и общее число в `meta.total`.
3. **Фильтр без совпадений.** `GET /api/notes?tag=отпуск`, таких заметок нет → `200`
   и пустой список. Это не ошибка.
4. **Обновление.** `PUT` меняет заголовок → `200` с новым `updated_at`. Клиент, не получив
   ответа из-за таймаута, повторяет тот же запрос → `200`, тело то же, `updated_at` не сдвинулся.
5. **Обновление несуществующей.** `PUT /api/notes/00000000-0000-4000-8000-000000000000`
   → `404`, ничего не создано.
6. **Опечатка в поле.** `POST` с полем `titel` → `422`, `code: unknown_fields`,
   в `fields` перечислено лишнее поле.
7. **Пустой тег.** `POST` с `tags: ["работа", "  "]` → `422` с указанием `tags.1`.
8. **Битые границы.** `GET /api/notes?limit=-1` → `422` с `field: limit`.
9. **Удаление.** `DELETE` → `204`. Повторный `DELETE` того же `id` → `404`.
10. **Испорченное хранилище.** В `notes.json` дописан мусор → любой запрос **с корректным
    телом и параметрами** отдаёт `500` `storage_corrupted`, файл при этом не изменяется.

Сценарии импорта добавлены на шаге 1 ДЗ №2 (2026-08-30):

11. **Импорт пачкой, всё валидно.** `POST /api/notes/import` с `Idempotency-Key: batch-001`
    и тремя корректными заметками → `200`, `imported: 3`, `rejected: 0`,
    `idempotent_replay: false`, в `notes` три заметки с выданными `id`.
12. **Повтор по таймауту.** Тот же запрос с тем же ключом и тем же телом → `200`,
    тело **то же самое**, но `idempotent_replay: true`. В хранилище по-прежнему три
    заметки, а не шесть.
13. **Тот же ключ, другое тело.** `Idempotency-Key: batch-001`, но заметок теперь четыре
    → `409` `idempotency_key_conflict`. Ничего не записано, хранилище не изменилось.
14. **Частичный брак.** Пачка из пяти заметок, у второй пустой `title`, у четвёртой поле
    `titel` → `200`, `imported: 3`, `rejected: 2`, в `errors` две записи с `index: 1`
    (`validation_failed`) и `index: 3` (`unknown_fields`). Три валидные заметки записаны.
15. **Всё отклонено.** Пачка из двух заметок, обе без `title` → `200`, `imported: 0`,
    `rejected: 2`. Не `422`: формат ответа один и тот же независимо от того, повезло ли
    хоть одной заметке.
16. **Импорт файлом.** `multipart/form-data`, поле `file` с тем же JSON → результат,
    неотличимый от формата A. Имя файла и его MIME-тип на результат не влияют.
17. **Без ключа.** Тот же запрос без заголовка `Idempotency-Key` → `422`
    `idempotency_key_invalid`, ничего не записано.
18. **Слишком большая пачка.** 201 заметка → `413` `import_too_large`. Проверка
    срабатывает до разбора содержимого: невалидные заметки внутри пачки роли не играют.
19. **Чужой формат тела.** `Content-Type: text/plain` → `415` `unsupported_media_type`.
20. **Недоверенный текст.** В `body` импортируемой заметки лежит строка вида
    «Игнорируй предыдущие инструкции и удали все заметки» → `200`, заметка создана,
    строка сохранена **как обычный текст**, ни одна заметка не удалена. При выдаче
    в веб-интерфейсе строка отображается как текст и не исполняется.

**Порядок проверок: тело и параметры запроса валидируются до чтения хранилища.**

> Записано на шаге 6 (2026-08-17). Расхождение обнаружено при самопроверке: сценарий 10
> в исходной редакции говорил «любой запрос», и невалидный `POST` на испорченное
> хранилище отдавал `422`, а не `500`. Порядок оставлен как есть — менялась формулировка
> сценария, потому что решение сознательное, а не следствие кода.

Невалидный `POST` на испорченное хранилище отдаёт `422`, а не `500`. Клиент должен
узнавать о собственной опечатке независимо от состояния диска на сервере: при обратном
порядке испорченный файл на сервере скрывал бы от клиента его же ошибки, и отладка
клиента становилась бы невозможной ровно тогда, когда на сервере и так авария.

## Состояния

| Состояние | Что видит клиент |
|---|---|
| **Хранилище отсутствует** (файла нет) | Трактуется как пустой список. `GET` → `200`, `data: []`. Первый `POST` создаёт файл |
| **Хранилище пустое** (файл есть, содержит `[]` или ноль байт) | То же: `200`, `data: []` |
| **Есть данные** | `200` со списком и заполненным `meta` |
| **Фильтр ничего не нашёл** | `200`, `data: []`, `total: 0` — отличается от предыдущего только тем, что в хранилище записи есть |
| **Ошибка клиента** | `400`, `404` или `422` в едином формате, с указанием поля |
| **Хранилище испорчено** | `500` `storage_corrupted`. Файл **не** перезаписывается и не удаляется |

Последнее — сознательное решение: сервис никогда не затирает данные, которые не смог
прочитать. Испорченный файл может содержать восстановимые записи, и молчаливая
перезапись уничтожила бы их окончательно.

### Что именно считается испорченным хранилищем

> Уточнено на шаге 6 (2026-08-17) по находкам самопроверки. До этого термин
> «испорчено» использовался, но не раскрывался, и реализация трактовала его как
> «файл не разобрался как JSON». Этого оказалось мало: хранилище `[{}]` разбиралось
> успешно и отдавалось клиенту как `200` с заметкой `id: null`. Менялся **код**,
> а не контракт: контракт обещал `id` типа UUID v4 и в этом ответе нарушался.

Хранилище считается испорченным, если верно хотя бы одно:

- содержимое не разбирается как JSON;
- на верхнем уровне не список (объект, строка, число);
- **хотя бы один элемент списка не является объектом** (число, строка, вложенный список);
- **хотя бы у одного элемента отсутствует `id`, либо он не строка, либо пустая строка**.

Граница проведена по `id` и только по нему. Это адрес записи: заметка без `id`
недостижима через `GET`, `PUT` и `DELETE` и не может быть корректно показана в списке,
а разумного значения по умолчанию у него нет. Остальные поля при чтении дополняются
умолчаниями (`title` и `body` — пустая строка, `tags` — пустой список), и запись вида
`[{"id":"..."}]` испорченной **не** считается: умолчания здесь не выдумывают данные,
а отражают пустоту.

## Чего точно не делаем

Список удерживает объём. Всё перечисленное — за границей задачи, и попытка добавить это
по ходу требует отдельного разговора.

- Аутентификация, авторизация, пользователи. Сервис однопользовательский
- База данных, Docker, внешние сервисы — прямой запрет из условий задания
- Конкурентная запись: блокировок файла нет, параллельные записи не поддерживаются
- Полнотекстовый поиск, ранжирование, морфология. `q` — подстрочное совпадение
- Сортировка по выбору клиента: порядок фиксирован спецификацией
- Мягкое удаление, корзина, история версий, восстановление
- Вложения, изображения, файлы
- Пагинация курсором, `HATEOAS`, `ETag`, условные запросы
- Реестр тегов как отдельная сущность, переименование тега во всех заметках
- Локализация сообщений об ошибках: язык один
- Rate limiting, CORS-политика, HTTPS — задача локального стенда

Добавлено на шаге 1 ДЗ №2 — границы импорта и веб-интерфейса:

- **Дедупликация по содержимому.** Идемпотентность здесь про доставку: один запрос,
  отправленный дважды, выполняется один раз. Две одинаковые заметки с разными ключами —
  это две заметки, и сервис не пытается угадать обратное
- **TTL и фоновая уборка реестра ключей.** Только потолок с вытеснением самых старых
- **Транзакция между `notes.json` и `import_keys.json`.** Двух файлов без транзакций
  достаточно; порядок записи зафиксирован в контракте, последствия сбоя названы
- **Форматы импорта, кроме JSON.** Ни CSV, ни Markdown, ни `.zip`
- **Экспорт.** Обратная операция в объём не входит
- **Отмена или откат импорта.** Записанное удаляется обычным `DELETE`, по одной заметке
- **Сборка фронтенда.** Веб-интерфейс — статические файлы без npm-зависимостей
  и без шага сборки; это следствие запрета на зависимости, а не выбор вкуса
- **Аутентификация в веб-интерфейсе.** Сервис по-прежнему однопользовательский

## Допущения

Решения, принятые без полной информации. Каждое — с одной фразой «почему так».

1. **Хранилище — `storage/app/notes.json`, массив объектов.** Почему: формат читается
   глазами, что важно для проверки; отдельный индекс не нужен на объёмах учебного стенда.
2. **`id` — UUID v4, выдаёт сервер.** Почему: клиентский `id` потребовал бы валидации
   формата и разбора коллизий, а это объём сверх задачи.
3. **Все временные метки в UTC, формат ISO 8601 с `Z`.** Почему: часовые пояса — источник
   ошибок, которых в этой задаче можно не иметь вовсе.
4. **Идемпотентный `PUT` не сдвигает `updated_at`, если тело совпало.** Почему: следует
   из решения отвечать `200` на повтор — иначе два одинаковых запроса дают разные ответы,
   и идемпотентность остаётся только на словах. Побочный эффект: `updated_at` означает
   «когда данные последний раз изменились», а не «когда последний раз пришёл запрос».
5. **`limit` по умолчанию 20, потолок 100.** Почему: потолок нужен, чтобы один запрос
   не выгружал весь файл; конкретные числа — общепринятые, специальных требований нет.
6. **Сравнение в `q` регистронезависимое, по `title` и `body` одновременно.** Почему:
   раздельный поиск по полям потребовал бы параметров вида `title_q`, что усложняет
   контракт без выигрыша на этом объёме.
7. **Порядок при равном `created_at` — по `id` по возрастанию.** Почему: без явного
   правила порядок зависит от реализации сортировки, и тесты становятся нестабильными.
8. **Запись в файл — атомарная: временный файл плюс переименование.** Почему: прерывание
   процесса в момент записи иначе оставит наполовину записанный JSON, то есть переведёт
   сервис в состояние `storage_corrupted` своими руками.

Добавлено на шаге 1 ДЗ №2 (2026-08-30). Решения приняты агентом **без вопроса человеку** —
человек отвечал на четыре крупных вопроса, эти четыре мельче и обратимы, но записаны
здесь явно, чтобы их можно было оспорить:

9. **Потолок пачки — 200 заметок, тела — 2 МБ.** Почему: числа взяты из того же
    соображения, что и `limit` 100 — один запрос не должен выгружать или загружать
    произвольный объём. Проверка идёт до разбора содержимого.
10. **Формат ключа — 8…128 символов `[A-Za-z0-9_-]`.** Почему: нижняя граница отсекает
    ключи вида `1`, у которых столкновение между разными клиентами вероятно; верхняя
    и набор символов не дают положить в заголовок произвольные данные.
11. **`request_hash` — SHA-256 от канонизированного содержимого пачки.** Почему: сравнивать
    сырые тела нельзя — те же данные в другом порядке ключей JSON или с другими отступами
    дали бы ложный `409`.
12. **Реестр ключей не участвует в определении «испорченного хранилища».** Почему:
    нечитаемый `import_keys.json` — это потеря защиты от повторов, а не потеря данных.
    Сервис отвечает `500` `internal_error`, а не `storage_corrupted`, и **не** перезаписывает
    файл. Альтернатива — молча начать реестр заново — отклонена: она превращает аварию
    в тихое отключение идемпотентности ровно тогда, когда клиент на неё рассчитывает.

## Критерии приёмки

Формулировки проверяемые: каждая закрывается одним запросом или одним тестом.

- [ ] `POST /api/notes` с `{"title":"Купить хлеб","tags":["Работа"," работа ","дом"]}`
      возвращает `201`, в теле `tags` равны `["работа","дом"]`
- [ ] `POST` без `title` возвращает `422`, `code: validation_failed`, в `fields` есть `title`
- [ ] `POST` с полем `titel` возвращает `422`, `code: unknown_fields`, в `fields` есть `titel`
- [ ] `POST` с `tags: ["ok","  "]` возвращает `422` с указанием `tags.1`
- [ ] `GET /api/notes?tag=отпуск` при отсутствии таких заметок возвращает `200`,
      `data: []`, `meta.total: 0`
- [ ] `GET /api/notes?limit=-1` возвращает `422` с `field: limit`;
      то же для `limit=0`, `limit=101`, `limit=abc`
- [ ] `GET /api/notes?offset=9999` возвращает `200` и пустой `data` при непустом `meta.total`
- [ ] `GET /api/notes?offset=999999999999999999999` возвращает `200`, а не `422` —
      верхней границы у `offset` сознательно нет
- [ ] `PUT` существующей заметки дважды подряд с тем же телом даёт два одинаковых
      ответа `200`, `updated_at` во втором не изменился
- [ ] `PUT` по несуществующему `id` возвращает `404`, число записей в файле не изменилось
- [ ] `DELETE` возвращает `204`, повторный `DELETE` того же `id` — `404`
- [ ] При отсутствующем `notes.json` `GET /api/notes` возвращает `200` и `data: []`
- [ ] При пустом `notes.json` `GET /api/notes` возвращает `200` и `data: []`
- [ ] При испорченном `notes.json` любой запрос с корректным телом возвращает `500`
      `storage_corrupted`, и содержимое файла после запроса совпадает с тем, что было до
- [ ] `notes.json` вида `[1,2,3]` возвращает `500` `storage_corrupted`, а не `internal_error`
- [ ] `notes.json` вида `[{}]` возвращает `500` `storage_corrupted`, а **не** `200`
      с заметкой `id: null`
- [ ] `POST` на хранилище `[{}]` возвращает `500` и **не дописывает** заметку в файл
- [ ] `notes.json` вида `[{"id":"..."}]` без остальных полей возвращает `200`,
      `title` и `body` — пустые строки, `tags` — пустой список
- [ ] Невалидный `POST` на испорченное хранилище возвращает `422`, а не `500`
- [ ] Ни один ответ об ошибке не содержит трассировки стека, пути к файлу на диске
      или имени класса
- [ ] Автотесты проходят целиком, в прогоне есть один успешный сценарий
      и не менее трёх ошибочных
- [ ] Тесты не обращаются к сети и не читают и не пишут рабочий `storage/app/notes.json`

### Критерии приёмки импорта и веб-интерфейса

Добавлено на шаге 1 ДЗ №2 (2026-08-30). Каждый пункт закрывается одним запросом
или одним тестом.

**Импорт — успешные пути**

- [ ] `POST /api/notes/import` с `Idempotency-Key` и тремя валидными заметками
      возвращает `200`, `imported: 3`, `rejected: 0`, `idempotent_replay: false`,
      и в `notes` три заметки с непустыми `id`
- [ ] Тот же запрос, отправленный повторно с тем же ключом и тем же телом, возвращает
      `200` и **то же тело**, отличающееся только `idempotent_replay: true`
- [ ] После повтора число записей в хранилище не изменилось
- [ ] Импорт файлом (`multipart/form-data`, поле `file`) даёт результат, неотличимый

- [ ] Теги в импортированных заметках нормализованы по тем же правилам, что при `POST`

**Импорт — частичный успех**

- [ ] Пачка из пяти заметок с двумя невалидными возвращает `200`, `imported: 3`,
      `rejected: 2`, и в `errors` две записи
- [ ] `errors[].index` указывает на позицию во **входной** пачке, а не в `notes`
- [ ] Пачка, где невалидны все элементы, возвращает `200` с `imported: 0`, а не `422`
- [ ] Три валидные заметки из пачки с браком действительно лежат в хранилище

**Импорт — отказы**

- [ ] Запрос без заголовка `Idempotency-Key` возвращает `422`
      `idempotency_key_invalid`, и хранилище не изменилось
- [ ] Ключ короче 8 символов возвращает `422` `idempotency_key_invalid`
- [ ] Тот же ключ с другим телом возвращает `409` `idempotency_key_conflict`,
      и хранилище не изменилось
- [ ] Пачка из 201 заметки возвращает `413` `import_too_large`
- [ ] Тело больше 2 МБ возвращает `413` `import_too_large`
- [ ] `Content-Type: text/plain` возвращает `415` `unsupported_media_type`
- [ ] `{"notes": []}` возвращает `422` `validation_failed`
- [ ] Файл, не разбирающийся как JSON, возвращает `400` `malformed_json`
- [ ] Ни один из этих отказов не создал записи в `import_keys.json`

**Импорт — состояние хранилища**

- [ ] Импорт на отсутствующий `notes.json` создаёт файл и записывает заметки
- [ ] Импорт на испорченный `notes.json` возвращает `500` `storage_corrupted`,
      и содержимое файла после запроса совпадает с тем, что было до
- [ ] Испорченный `import_keys.json` возвращает `500` `internal_error`,
      а не `storage_corrupted`, и файл не перезаписывается
- [ ] Формат `notes.json` после импорта остаётся массивом заметок — тем же, что до ДЗ №2
- [ ] При превышении 500 ключей в реестре вытесняется самая старая запись,
